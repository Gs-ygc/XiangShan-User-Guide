# 差分验证 {#sec:debug-difftest}

## 作用

差分验证（difftest）把香炉峰的执行结果与功能参考模型逐步比对，是矩阵扩展功能正确性的主要保障手段，也是"提交语义是否与规范一致"的最终裁判。

## 参考模型

* 支持 **CPU 参考模型**与 **GPU 参考模型**两条路径，可分别使用以排除参考侧实现差异；
* 矩阵指令支持 batching、反压与顺序检查；
* 参考模型对若干 **未定义行为**从"静默通过"改为"可检出错误"：读取未写入的矩阵寄存器区域、缺少 `mfence`、`macquire` 前访存违例等。

## 矩阵寄存器对比优化

早期实现需要把整个矩阵寄存器的每个元素逐条传输后比较。现改为**两侧各自计算哈希后比较**：

| 项 | 说明 |
| --- | --- |
| 收益 | 显著降低仿真器与参考模型之间的通信量 |
| 适用 | 结果唯一的运算（`mzero`、算术类等） |
| 不适用 | 存在误差容忍的乘法类指令（如 `mma`），因结果不唯一；同时参考模型侧需要在拿到 DUT 结果前继续推进 |
| 一致性 | 两侧输入相同时哈希必然相同；不同时哈希通常也不同 |

## 开销

差分验证并非免费，其开销已在多组负载上量化（同一二进制、同一随机种子、交错执行 diff / no-diff）：

| 负载 | 配置 | 开销 |
| --- | --- | --- |
| AME-MMACC | 固定 CPU（CPU 0–7） | +0.77% |
| CoreMark 5k 周期冒烟 | — | +0.91% |
| CoreMark 50k 周期冒烟 | — | +1.19% |
| CoreMark 完整负载 | — | +0.30% |

注意两点方法学约定：① 未固定 CPU 时测得的较大波动（如 17.10%）应归因于调度/频率变化，不能记为差分开销；② 只有"测量次数正确、两种模式状态稳定且一致、两模式指令数与周期数完全相同"时，该组比较才有效。

## 使用建议

1. 日常最小验证默认开启（`DIFF=1`），这是标准路径；
2. 出现 mismatch 时，先用 `DIFF=0` 排除差分接口自身问题，再判断是 RTL 还是参考模型；
3. 涉及矩阵寄存器的比较，优先使用已支持 hash 对比的指令范围，避免无谓的通信开销；
4. 参考模型与 DUT 的**配置必须一致**（例如裁剪配置对完整配置），否则会产生系统性误报。
